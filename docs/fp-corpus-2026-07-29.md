# Post-M3 informal false-positive corpus — 2026-07-29

## Purpose and scope

PLAN §6 requires an informal false-positive check immediately after M3 and
before the M4 signal layer. This run used the existing `scripts/fp-check.ts`
harness over 20 popular packages × 3 adjacent stable, nondeprecated releases:
60 version bumps in total. The harness selection is explicitly **not a
legitimacy attestation** (`scripts/fp-check.ts:109-127`); this is a review-noise
sample, not the formal M5 false-positive measurement (PLAN §7.4).

The selected mix covers:

- small utilities: `lodash`, `minimist`, `ms`, `semver`, `debug`;
- frameworks and network-facing libraries: `react`, `express`, `axios`,
  `dotenv`, `jsonwebtoken`;
- build tools and parsers: `typescript`, `vite`, `esbuild`, `acorn`,
  `commander`;
- archive, native, and ecosystem packages: `tar`, `glob`, `sharp`,
  `node-fetch`, `better-sqlite3`.

The harness fetched registry metadata and tarballs, verified each tarball's
SHA-512 integrity, safely extracted it, and ran the manifest + AST capability
pipeline (`scripts/fp-check.ts:46-103`). It never installed or executed package
code. Because the harness constructs `ChangedPackage` pairs directly, this run
measures artifact capability findings and diagnostics; it does not exercise
lockfile-level downgrade/integrity findings or Action delivery.

## Diagnostic inspection

The corpus produced 1,258 diagnostics across 33 bumps and 11 packages. They
were highly concentrated rather than evidence of 1,258 distinct review risks:

- TypeScript produced 664 diagnostics by itself. Targeted grouping found 654
  `unsupported-source` diagnostics for `.d.ts` declaration files and 10
  `unparseable-source` diagnostics for JavaScript files above the 2 MiB parser
  limit.
- Representative commander and glob diagnostics were also `.d.ts` declaration
  files. Packages such as tar and Vite repeated the same pattern on both sides
  of every bump.
- Declaration files are not runtime JavaScript. Reporting each one separately
  satisfies the current literal `.ts` rule but creates substantial noise in the
  full JSON/text report without identifying executable code.
- Oversized executable JavaScript is different: it represents genuinely
  unanalyzed runtime data and should remain loud until the M4 blob/signal layer
  can classify it more usefully (PLAN §4.3, §6).

## Decisions and M4 tuning recommendations

These are evidence-backed recommendations from the corpus, not implementation
changes:

1. **Keep the current severity fallbacks and default CRITICAL gate.** No sampled
   bump produced CRITICAL/HIGH/MEDIUM, and none would have been falsely blocked
   by the default gate. LOW dependency/FS/UNKNOWN findings and INFO runtime
   constraints matched their intended review priority.
2. **Handle `.d.ts` declarations before adding new signals.** Propose a scoped
   JavaScript-extractor change that treats declaration files as non-executable
   metadata rather than emitting one unsupported-source diagnostic per file.
   The design must preserve loud handling for executable `.ts` and oversized
   `.js`; tests should distinguish `.d.ts`, runtime `.ts`, and large JavaScript.
3. **Refine, but do not suppress, `UNKNOWN`.** The better-sqlite3 dynamic native
   load is exactly the honest signal `UNKNOWN` exists for. The TypeScript result
   shows that deep member calls on literal relative/vendored imports can also
   collapse into a large LOW `UNKNOWN` finding. Before changing resolution,
   propose how to retain the originating module category so local-module member
   chains can be distinguished from dynamic module loads and unresolved Node
   APIs. The adversarial `require('child' + '_process') → UNKNOWN` invariant in
   PLAN §7.1 must remain.
4. **Consider comment-only aggregation for dependency additions.** Seven
   accurate jsonwebtoken dependency findings can consume most of the ten-row PR
   table. Global severity sorting already prevents them from hiding a higher
   priority finding (`src/action/action-comment-reporter.ts:263-289`), so this
   is presentation tuning only; JSON must retain every dependency fact.
5. **Do not add benign install-script suppression from this corpus yet.** The
   sampled install/native packages did not produce new install-hook findings,
   so this run supplies no evidence for ranking `node-gyp`, Husky, or
   patch-package patterns. That recognizer should wait for a corpus containing
   actual install-hook additions, as PLAN §6 requires.

## Checkpoint conclusion

The mandatory post-M3 informal corpus checkpoint is complete. The current
shape-based severity model did not over-escalate this sample, and the default
CRITICAL gate produced zero false blocks. The first scoped pre-signal M4 change
should be a design proposal for declaration-file diagnostic handling in the
JavaScript extractor, followed by the `UNKNOWN` provenance question if the
maintainer approves that interpretation. Formal TP/FP claims still belong to M5
and require the larger PLAN §7.4 corpus.
